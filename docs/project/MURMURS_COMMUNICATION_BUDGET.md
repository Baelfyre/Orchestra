# Murmurs Communication Budget

## Purpose

Murmurs reduces conversational progress narration during governed execution without reducing machine evidence, validation records, governance state, or the final explanation.

Core rule:

> Compress the representation, not the underlying truth.

Murmurs is a presentation feature. It is not an authority layer, evidence store, validation shortcut, or replacement for task-completion reporting.

## Modes

Orchestra exposes two presentation modes:

- `NORMAL`: routine events remain explanatory and are eligible for ordinary host/model narration.
- `MURMURS`: routine events may resolve to `SILENT` or a locally rendered `MURMUR`; safety-critical and terminal events remain `EXPLAIN`.

Adapters default to `NORMAL`. A host opts into Murmurs with metadata:

```text
orchestra.presentation_mode=MURMURS
```

All adapters delegate to the same machine presentation policy. Hosts do not maintain separate Murmurs vocabularies or reinterpret event safety.

## Machine contracts

The machine-owned presentation contracts are:

- `machine/presentation/murmurs-policy.v1.json`
- `machine/presentation/murmurs-vocabulary.v1.json`
- `machine/schemas/presentation-policy.schema.json`
- `machine/schemas/murmurs-vocabulary.schema.json`

The runtime implementation is `orchestra_runtime/presentation.py`.

The policy has three dispositions:

- `SILENT`: emit no conversational progress content.
- `MURMUR`: render a bounded non-semantic local filler without a model call.
- `EXPLAIN`: normal explanation is required.

The default policy is fail-closed to `EXPLAIN`.

## Required explanation boundary

The following event classes cannot be suppressed or murmured by policy:

- human action required;
- authority required;
- validation failed;
- unrecoverable blocker;
- governance stop;
- handoff required;
- task completed;
- task failed.

Missing, malformed, or unsafe presentation contracts also fail closed to `EXPLAIN`.

## Local deterministic renderer

Murmur text is not generated by the model. The renderer selects a vocabulary entry using a stable SHA-256-derived index over run identity, event sequence, and event kind.

This gives bounded variation without nondeterministic runtime behavior or prompt/context overhead from loading a filler vocabulary into the model.

Vocabulary entries are constrained to short, trimmed, single-line, non-semantic strings and reject status/completion terms such as `done`, `passed`, `failed`, `fixed`, or `success`.

## Lifecycle and authority boundary

Lifecycle signals are mapped into presentation events without changing the original lifecycle signal, fingerprint, evidence references, state transition, authority, or governance disposition.

Presentation decisions cannot:

- change machine state;
- override governance;
- create authority;
- suppress a required explanation.

The final explanation remains grounded in authoritative machine state and evidence rather than depending on intermediate chat narration.

## Measurement contract

Communication measurements are represented by `orchestra_runtime/communication_budget.py` and `machine/schemas/communication-measurement.schema.json`.

The contract separates deterministic communication measurements from model-specific token measurements.

Deterministic or host-observable fields include:

- progress-message count;
- model progress-call count;
- user-visible bytes;
- context bytes admitted;
- tool/result bytes admitted;
- repeated reads;
- communication overhead when supplied by the host;
- task outcome;
- validation digest;
- governance digest.

Token fields are source-qualified:

- `HOST_REPORTED`: requires a token-counter identity plus both input and output counts.
- `UNAVAILABLE`: token counts and counter identity must remain null.

Token deltas are calculated only when baseline and candidate both use the same host-reported counter identity. Orchestra does not estimate model tokens from characters, bytes, words, or a tokenizer for another model. It does not calculate percentage savings from incomparable counters.

Outcome parity is evaluated separately from communication reduction. A lower communication count is not accepted as an improvement if task outcome, validation identity, or governance identity changes.

## Caveman-derived design lessons

The Murmurs design adopts selected principles observed in Caveman/Caveman Code without wholesale integration:

- output communication and input/context load are separate optimization surfaces;
- repeated information should be referenced rather than repeatedly reconstructed when an authoritative reference exists;
- compression should be payload-aware rather than blind truncation;
- compressed representation must not destroy the ability to recover authoritative evidence;
- efficiency claims require measurement rather than assumption.

No Caveman runtime dependency or external source code is incorporated by this feature.

## Semantic tool/log output budgets

Lossy tool/log compression is **not promoted** in the initial Murmurs implementation.

Orchestra's current context-state runtime stores typed state, hashes, references, and continuity events, but it is not a general original-tool-output content store. Therefore replacing a tool result with a lossy compact representation could make omitted original content unrecoverable.

Before semantic tool/log compaction may become authoritative for model context, the implementation must prove all of the following:

1. original bytes/content are preserved in an authoritative retrievable location;
2. the compact representation carries an immutable recovery reference and content digest;
3. error/failure/security/governance-relevant material is not silently omitted;
4. truncation/compaction is deterministic and payload-aware;
5. recovery failure fails closed rather than treating the compact representation as complete evidence;
6. before/after measurements show material benefit without outcome or governance drift.

Repeated-read deduplication follows the same rule: a digest stub may replace repeated content only when the original remains retrievable through a stable evidence/content reference.

Until those requirements are implemented and validated, Murmurs optimizes the safer presentation-output surface only.

## Evidence levels

Repository CI can prove:

- deterministic dispositions;
- no model call is needed to render a murmur;
- normal/off behavior;
- forced explanation events;
- malformed-contract fail-closed behavior;
- lifecycle identity preservation;
- adapter parity;
- measurement-contract correctness;
- no invented token comparison when counters are unavailable.

Repository CI cannot by itself prove a percentage reduction in model billing tokens or end-to-end host latency.

Those claims require controlled baseline and Murmurs runs from a host that reports comparable token counters under the same scenario/model/counter identity. Until such evidence exists, release documentation must describe Murmurs structurally and must not claim an unmeasured savings percentage.

## Release boundary

Murmurs is a pre-release development task. Its implementation does not select SemVer, publish a tag or GitHub Release, mutate installed integrations, deploy, or grant release authority.

After Murmurs integration, the final integrated release candidate must refresh the release-hardening evidence tracked separately by #292, including fresh integrated mutation evidence and the complete protected validation matrix.
