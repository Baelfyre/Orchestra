## Release summary

Orchestra v1.8.0 is a post-v1.7 feature release candidate that consolidates the canonical development line around stronger governed execution, optimized Compliance Registry consumption, optional evidence-backed testing and specialist execution capabilities, improved MCP compatibility, and provenance-aware Cloak reference intelligence.

The release candidate preserves Orchestra's Prime Directive: capability, routing, model selection, learned state, validation success, compatibility evidence, mergeability, and successful host execution do not independently create authority.

This document describes a candidate only. The `v1.8.0` tag does not exist as part of this preparation, no GitHub Release is published by this work, and publication remains subject to separate final-review approval after exact-head qualification and canonical verification.

## Prime Directive and Development Lifecycle V2

The post-v1.7 line formalizes the Orchestra Prime Directive and separates implementation maturity from permanent capability promotion.

Development Lifecycle V2 adds explicit candidate declaration, feature freeze, qualification-gate planning, promotion adjudication, merge preparation, independent verification, and closeout/retirement boundaries.

The practical invariant remains:

```text
implemented != validated
validated != evidence-supported
validated != worth adopting
merge-ready != release authority
capability != permission
```

## Supported optional specialist host execution

The specialist runtime-host execution program completed E1 through E7 and reached `ADOPT_OPTIONAL` for the validated bounded Codex host-execution path.

The optional path retains route-only defaults, explicit user model configuration, authority and capability gates before provider execution, bounded host constraints, specialist-source identity binding, and fail-closed receipt validation.

The validated evidence includes bounded Codex read-only Scribe and Ponytail mutation fixtures. It does not establish generic MCP mutation end-to-end support, default runtime mutation, unrestricted host execution, provider-routing authority, or release/deployment authority.

## Provider execution and qualification boundaries

v1.8.0 includes provider execution profile and requirement contracts that keep provider identity, model identity, capability requirements, Orchestra authority, and host execution evidence separate.

The post-v1.7 line also adds a bounded Claude Code provider-native execution bridge and a VS Code multi-harness observation/qualification framework.

These surfaces do not create automatic provider routing or fallback, do not authorize credential or persistent host-setting mutation, and do not convert deterministic qualification evidence into claims of universal live-provider support.

## Compliance Registry O7 query optimization

O7.1 through O7.7 are canonical and consume the Registry R7 query surface using the smallest sufficient projection while preserving O1-O6 compliance semantics.

The optimized path includes optional capability negotiation, indexed/direct-JSON fallback behavior, `MINIMAL`/`SUMMARY`/`EVIDENCE`/`FULL` projection handling, existing compliance-receipt normalization, deterministic integrity checks, and joint conformance against the trusted Registry v0.4.0 release.

Registry MCP remains optional transport, not authority. Query or projection choice cannot change compliance meaning, and the completed R7.9 evidence did not establish a token-efficiency benefit claim.

## MCP 2026 compatibility and documentation parity

The post-v1.7 line improves the bounded MCP stdio path for the `2026-07-28` protocol revision, including Codex discovery compatibility with non-cacheable private discovery hints.

MCP continues to expose only the governed Orchestra tool surface and remains transport rather than execution authority. Installed-host refresh remains manual and separately authorized.

## Unified Testing Mechanism

The Unified Testing Mechanism provides an optional T0-T9 applicability and evidence-aggregation layer that reuses existing specialist and CI validation instead of creating a second testing engine.

Its controlled offline efficacy calibration passed the preregistered deterministic fixture thresholds and produced an `ADOPT_OPTIONAL` recommendation.

The evidence does not measure live-host operator time, live-host token cost, or live-host latency, and UTM remains non-mandatory and non-authorizing.

## Cloak UI reference intelligence, CUIR-0 through CUIR-6

The CUIR program is closed through CUIR-6 with the bounded CUIR-4 progressive retrieval capability adopted as supported optional Cloak behavior.

The canonical program establishes:

- CUIR-0 provenance, licensing, non-copying, and source-intake governance;
- CUIR-1 dated source inventory and per-source reuse classification;
- CUIR-2 bounded static concept-level analysis;
- CUIR-3 Orchestra-native normalized pattern knowledge;
- CUIR-4 bounded progressive retrieval with at most three problem classes and five patterns per task;
- CUIR-5 deterministic controlled evaluation against a no-CUIR-retrieval baseline;
- CUIR-6 `ADOPT_OPTIONAL` closeout for the existing bounded retrieval layer.

The CUIR evidence preserves project-native precedence, source provenance, license/reuse classifications, icon-rights distinctions, non-copying boundaries, disabled full-corpus injection, disabled automatic host injection, and separate implementation authority.

CUIR-5 does not establish end-to-end LLM output quality, rendered visual correctness, human usability preference, or production effectiveness. The optional CUIR-6 adoption does not widen those claims.

## UIX-9C terminal controlled-study evidence

The post-v1.7 UIX-9C V3 controlled study completed with six valid observations and three corrected valid pairs.

All 39 primary governed-versus-baseline comparisons were unchanged, producing terminal `NO_BENEFIT_ESTABLISHED` evidence. This establishes neither repeatable governed benefit nor harm under the frozen study.

The null result remains preserved as evidence and does not authorize repeated experimentation until a positive result appears.

Murmurs remains optional/historical presentation research, and A5 remains closed without execution-effective topology promotion.
