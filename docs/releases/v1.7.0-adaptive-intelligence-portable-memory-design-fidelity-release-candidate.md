# Orchestra v1.7.0: Adaptive Intelligence, Portable Memory & Design Fidelity

## Release summary

Orchestra v1.7.0 is a feature release focused on three major improvements: **adaptive intelligence with bounded memory**, **governed UI design fidelity**, and **more capable compliance-context consumption**.

The release consolidates the substantial post-v1.6 development line while preserving Orchestra's central trust rule: learned state, external tools, validation success, compatibility evidence, and mergeability do not create authority.

The v1.7.0 release line adds adaptive behavior only inside deterministic governance and execution ceilings. It also introduces a storage-agnostic portable-memory contract so users and organizations can choose how approved learned patterns are stored without coupling Orchestra to a particular repository, database, provider, or service.

## Adaptive intelligence and scoped local memory

Orchestra now includes a governed adaptive-learning foundation for retaining and evaluating recurring user, project, specialist, and workflow patterns.

### A1: machine-local adaptive memory

A1 provides scoped local observation and preference evidence with provenance, confidence, and lifecycle state. It separates explicit preferences from inferred patterns and keeps learned state machine-local by default.

Adaptive state cannot create authority, change governance, silently expand capabilities, or mutate canonical routing.

### A2: bounded specialist context

A2 allows specialists to receive only the relevant permitted subset of adaptive state for the current repository, project, specialist, and task.

The complete adaptive profile is not injected by default. Context remains advisory and is attached only after existing routing, authority, capability, and governance gates.

### A3: shadow behavioral learning

A3 can extract behavioral signals, accumulate evidence-backed candidate patterns, and compare learned recommendations with deterministic choices.

A3 remains shadow-only. Confidence is not authority, generic task success is not automatically strategy-success evidence, and a learned recommendation cannot select execution by itself.

### A4: bounded shadow selection

A4 evaluates already-eligible specialist strategies and model/worker tendencies while preserving deterministic eligibility and fallback.

The layer includes bounded post-execution observation attachment so later evidence can be recorded without allowing the adaptive selector to influence operation inputs or create new eligibility.

### A5: shadow topology evaluation

A5 evaluates eligible specialist coordination sequences under the existing Conductor, Tuner, specialist-ownership, Arbiter, and validation boundaries.

The comparative evidence did not establish sufficient measurable benefit for execution-effective topology promotion. A5 therefore closes at shadow maturity and deterministic coordination remains the effective execution path.

## Portable adaptive memory

v1.7.0 adds a **storage-agnostic portable-memory contract** for explicitly reviewed learned candidates.

Orchestra does not require or identify a specific external memory backend. Generic adapter classes include:

- `LOCAL_JSON`
- `GIT_JSON`
- `HTTP_API`
- `CUSTOM`

This allows users and organizations to choose local files, private Git-backed storage, an internal service/database bridge, or another custom adapter without changing Orchestra's adaptive-learning core.

Portable candidates are privacy-minimized. They exclude raw conversation, credentials, sensitive data, and local user/session identity. Backend credentials and implementation details remain external configuration.

Portable memory is advisory transport only. Staging or transporting a learned candidate does not make it canonical memory and cannot grant execution, routing, policy, governance, release, deployment, or other protected authority.

## Governed UI design fidelity

The UIX program introduces a structured, evidence-bound workflow for preserving design intent during AI-assisted implementation.

### UIX-0: ownership and overlap audit

Defines responsibility boundaries for UI design-fidelity work and prevents new contracts from silently duplicating existing specialist or governance ownership.

### UIX-1: UI Design Contract

Introduces a machine-readable contract for design-source identity, design-system tokens, layouts, themes, assets, accessibility requirements, component reuse mappings, fidelity dispositions, and revision-bound validation state.

### UIX-2: design-source preservation

Preserves source identity, evidence inventory, project-native component and token mappings, asset provenance, unresolved inputs, and pre-implementation handoff state.

### UIX-3: profile registry

Separates UI foundations, layouts, complete themes/systems, and optional effects with deterministic composition and accessibility invariants.

### UIX-4: component and asset preservation

Adds evidence for component mappings, variants, interaction states, semantic tokens, assets, substitutions, provenance, and intentional deviations.

### UIX-5: specialist integration

Aligns Conductor, Cloak, Clockwork, Governor, Ponytail, Overseer, and Arbiter around the same governed UI evidence while retaining their existing non-overlapping responsibilities.

### UIX-6: optional adapter boundaries

Defines explicit boundaries for optional Figma, Code Connect, Storybook, Playwright, axe, and project-native token tooling.

These tools remain optional capabilities and evidence sources. Their availability does not make them authoritative and does not authorize dependency adoption, installed-integration refresh, or Figma mutation.

### UIX-7: deterministic validation recovery

Strengthens the deterministic validation chain used by the UI design-fidelity program and preserves exact signed evidence through recovery.

### UIX-8: portable specialist parity

Preserves source specialist guidance across supported host projections while keeping no-copy and scaffold-only boundaries explicit.

### UIX-9A: controlled-proof preparation

Provides a frozen controlled-proof protocol with baseline and governed arms, deterministic positive and negative fixtures, and objective design-fidelity observations.

UIX-9A is proof infrastructure only. No live UIX-9 model/provider execution is included in v1.7.0 and the repository-only protocol does not establish a model-behavior improvement claim.

## Adaptive Compliance Registry consumption

The O1-O6 program expands Orchestra's governed Compliance Registry consumption path.

v1.7.0 includes:

- negotiated Registry capability handling;
- fail-closed compatibility checks;
- multi-jurisdiction query selection;
- query-scoped freshness validation bound to the exact consumed source set;
- release-delta impact analysis;
- governed domain-to-specialist resolution;
- an adaptive Registry consumer CLI;
- Registry query binding to Orchestra's compliance-receipt protocol;
- exact capability fixtures and joint Registry-Orchestra contract validation;
- deterministic handling of stale, mismatched, unknown, or unverifiable Registry evidence.

Registry evidence remains evidence, not authority. It cannot bypass Conductor routing, Governor applicability decisions, Steward traceability requirements, Arbiter set-equality checks, or explicit execution boundaries.

## Research and validation closeout

The post-v1.6 line completed substantial comparative measurement across Antigravity and Codex evidence paths.

The governed terminal conclusions are intentionally conservative:

- A5 topology benefit: **not established**.
- Murmurs repeatable efficiency benefit: **not established**.
- A5 plus Murmurs interaction promotion: **not eligible and not run**, because prerequisite benefit evidence was not established.

Murmurs therefore remains optional/historical presentation research rather than a default execution feature or specialist requirement.

Detailed benchmark tables are no longer embedded in the landing README. Evidence remains available under:

- `docs/benchmarking/`
- `machine/benchmarking/`
- `docs/history/CHANGELOG_PRE_V1_7.md`

Negative and inconclusive results are retained as provenance so they are not silently discarded or misrepresented as product benefits.

## Compatibility and authority boundaries

v1.7.0 does not change Orchestra's fundamental trust model.

The following remain explicit invariants:

```text
learned state != execution authority
confidence != permission
routing != authority
validation success != authorization
mergeability != release readiness
Registry evidence != authority expansion
UI design evidence != implementation authority
memory backend selection != policy activation
host compatibility != runtime authority
```

In addition:

- automatic adaptive-policy promotion remains disabled;
- automatic external-memory promotion remains disabled;
- backend identity and credentials remain user-controlled external configuration;
- optional design tools remain optional;
- scaffold-only hosts do not become supported runtime hosts because their manifests carry the v1.7.0 package identity;
- release publication does not authorize deployment, production mutation, installed-integration refresh, policy activation, destructive cleanup, force push, or history rewrite.

## Validation requirement

The release candidate must pass the complete exact-head release matrix before publication:

- Governance Check;
- validate/runtime tests and required coverage evidence;
- Required Analysis Compatibility / CodeQL;
- native Windows, Ubuntu, and macOS validation;
- required mutation/confidence evidence;
- signed materialization and exact-tree verification where required by the canonical release workflow;
- reviewed-tree, canonical-tree, signature, and sole-parent verification.

The `v1.7.0` tag and GitHub Release are authoritative only after they resolve to the exact approved signed canonical release commit and post-publication identity verification succeeds.
