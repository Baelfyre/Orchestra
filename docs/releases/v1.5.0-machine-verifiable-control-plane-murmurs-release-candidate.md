# Orchestra v1.5.0 Machine-Verifiable Control Plane and Murmurs

Status: `PREPARED_NOT_RELEASED`

Current public release while this candidate is under validation: `v1.4.0`.

## Release purpose

v1.5.0 packages the completed control-plane re-foundation, its forward governance stabilization, and the additive Murmurs communication-budget presentation layer into one release candidate.

The version is a minor release because the reviewed public package, command, specialist, and host surfaces remain present. Compatibility names retained by the re-foundation are derived from canonical machine contracts rather than removed, and Murmurs is opt-in with `NORMAL` as the default presentation mode. No supported host is promoted or demoted by the version change.

## Machine-verifiable control plane

The re-foundation establishes the operating rule `Agents reason. Machines attest.` Exact identifiers, command outcomes, routing defaults, governance classifications, transition dispositions, evidence freshness, compliance set equality, host capability, remediation bounds, and canonical promotion state are represented by versioned machine contracts and deterministic validators rather than agent prose.

The migration sequence reached `LEGACY_RETIRED`. Duplicate independently maintained runtime authorities were retired while compatibility APIs remain derived, non-normative views. Installed integrations were not mutated by the migration.

A later stabilization repaired autonomous merge readiness so `mergeable=true` alone can never authorize ordinary progression. The current PR read must also report `mergeable_state=clean`; unknown or non-clean states fail closed, and bypass capability is not governance authorization.

## Murmurs communication budget

Murmurs is an opt-in presentation layer that reduces routine progress narration without changing machine state, validation evidence, governance decisions, blockers, handoffs, or terminal reporting.

- `NORMAL` remains the host default.
- `MURMURS` is explicitly selected through the host presentation setting.
- Routine events may resolve to `SILENT` or a locally rendered deterministic `MURMUR`.
- Human-action, authority, validation-failure, blocker, governance-stop, handoff, completion, and failure events remain hard-bound to `EXPLAIN`.
- Filler is selected locally using deterministic hashing; the model does not generate it and the vocabulary is not injected into model context.
- Repository simulation demonstrates structural progress-call reduction with execution, validation, and governance identity parity. It does not establish a billing-token savings percentage. Token deltas are reported only when comparable host-reported counters exist.

Caveman-inspired lossy tool/log compaction remains unpromoted until authoritative originals can be recovered through immutable references and measured benefit is demonstrated.

The release candidate is being regenerated after Murmurs rather than reusing pre-Murmurs evidence. The final publication gate requires fresh exact-head evidence for:

- behavior and runtime tests;
- statement and branch coverage;
- critical control-plane coverage floors;
- workflow-sanity and incident regressions;
- P9 conformance;
- bounded Mutmut evidence;
- integrated Cosmic Ray evidence;
- Windows, Ubuntu, and macOS validation;
- CodeQL and governance checks;
- package/version parity across all 11 release surfaces;
- README, README.json, CHANGELOG, PROJECT_STATE, ROADMAP, and machine release-evidence parity.

A pre-version diagnostic checkpoint reached 1,055 passing runtime tests, 98.47% statement coverage, and 95.36% branch coverage. Those values are not final release authority because the version and release-document revision changes the source head. Fresh evidence must be produced on the actual final candidate.

## Compatibility and boundaries

v1.5.0 is intended as an additive, backward-compatible minor release. The release does not introduce MCP. MCP remains a subsequent campaign built from the independently verified v1.5.0 baseline and may be used as a portable transport without becoming a source of authority.

This preparation does not itself create a Git tag or GitHub Release. It performs no marketplace publication, deployment, installed-integration refresh, policy activation, ruleset bypass, branch deletion, force push, history rewrite, or destructive cleanup.

## Publication gate

Publication is permitted only from the exact signed canonical commit that passes the complete protected release matrix. The final tag and GitHub Release must resolve to that exact commit and be independently verified as non-draft and non-prerelease. Release publication does not imply marketplace publication or installed-host refresh.
